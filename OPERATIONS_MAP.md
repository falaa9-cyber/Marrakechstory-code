# Admin Operations Map

Open `/#admin`, sign in as authorized staff, then choose **Operations Map**. The board listens for booking changes through Supabase Realtime, refreshes every 60 seconds as a fallback while open, and can be refreshed manually. The `bookings` Realtime publication was enabled in production on 2026-09-17; the migration enables it idempotently elsewhere. Existing booking RLS policies still govern event visibility. The board uses the same authenticated `bookings` and `suppliers` queries as the rest of the admin console; no service-role key is used in the browser.

The default 30-day map shows relevant services. Its agenda lists all active bookings before upcoming departures. Hovering a booking previews its full route; selecting it expands a day-by-day timeline and focuses the map. Hovering or selecting an itinerary stop zooms to and highlights its matching marker, route segment, and safe-text detail tooltip. Today's services appear first in authored itinerary order, earlier days and completed timed stops are muted, and future days remain prominent. The clock uses `Africa/Casablanca`; a scheduled stop is labelled **NOW** from 30 minutes before until 30 minutes after its listed time. Stops with non-numeric times remain on the Today timeline rather than being incorrectly marked completed. Route animation respects reduced-motion preferences.

The booking editor now has accommodation location fields and optional operational fields on each daily-itinerary activity. Enter a complete address and verified WGS84 latitude/longitude to place a marker. Pickup and drop-off points can have separate coordinates. An address without coordinates stays in the agenda and triggers an alert; the map never guesses a position from free text. Use an airport, transfer, restaurant, tour, or activity type to classify each stop. Assign a supplier, driver, and/or guide and mark confirmed when arranged.

The map requests a road-following driving geometry for each focused journey from the public OSRM router and renders it as a Google-Maps-style blue route with a white casing. If the router is unavailable, it visibly falls back to a planning connector; it never presents that fallback as navigation. Clusters are rendered locally from the authorized data. Assignment conflicts currently mean the same collaborator is scheduled at the exact same date and time on different bookings; travel-time or capacity conflicts require a later scheduling model.

Apply `supabase/migrations/20260917_operations_map.sql` to environments that have not received the four additive booking columns. Existing `daily_itinerary` JSON and all existing booking fields remain compatible. The production Supabase project received those columns on 2026-09-17. New activity fields live within the existing `daily_itinerary` JSON, so no extra public table or RLS policy is required.

## Google Maps styling and API configuration

The current map defaults to the branded light OpenFreeMap Positron basemap and keeps Night, Liberty, Terrain, and Satellite alternatives. OpenFreeMap's public instance is free, commercial use is allowed, and it does not require registration or API keys; MapLibre automatically supplies the required attribution. Its documented styles are integrated through MapLibre using URLs such as `https://tiles.openfreemap.org/styles/positron` and `https://tiles.openfreemap.org/styles/liberty` ([quick start](https://openfreemap.org/quick_start/), [service details](https://openfreemap.org/)).

Google Cloud styling remains optional. If the Google project is later enabled, set `VITE_GOOGLE_MAPS_API_KEY` and `VITE_GOOGLE_MAP_ID` in the deployment environment. Google documents that relationship in the [Map ID styling guide](https://developers.google.com/maps/documentation/javascript/examples/map-id-style) and the [cloud customization overview](https://developers.google.com/maps/documentation/javascript/map-ids/customize-maps-overview).

When the Google project is ready, set `VITE_GOOGLE_MAPS_API_KEY` and `VITE_GOOGLE_MAP_ID` in the deployment environment. `vite.config.js` copies them into `window.MS_ENV` at build time; neither value is hard-coded in the repository. Restrict the browser key to the production hostname and local development origin, enable Maps JavaScript API (and Places/Routes only if those APIs are enabled for the project), then rebuild. The existing operations data, route geometry, booking markers, addresses, and calendar remain the source of truth.
